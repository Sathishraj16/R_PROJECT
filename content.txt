1. WHAT IS SCAMTRACER AI?
================================================================================

ScamTracer AI is a cyber-security and scam-intelligence system that detects
scam conversations in real time (via WhatsApp), alerts the user, and — with
the user's explicit consent — engages the scammer in a controlled manner to
extract actionable intelligence for investigation purposes.

The system is built as a college project demonstration of the H.I.V.E.
architecture using R as the primary analytical engine and Node.js as the
communication/integration layer.

Key goals:
  - Automatically detect scam messages using NLP and machine learning.
  - Notify the user when a suspicious message is detected.
  - Give the user two choices: BLOCK & PROTECT (exit safely) or ACTIVATE
    H.I.V.E. (begin controlled engagement).
  - If H.I.V.E. is activated, engage the scammer with probing responses to
    extract verifiable intelligence: phone numbers, UPI IDs, URLs, bank names,
    transaction references, OTP requests, payment requests, etc.
  - Analyse the scammer's behaviour patterns: urgency, threats, impersonation,
    escalation, repeated requests.
  - Display everything in a structured R Shiny investigation dashboard.

CRITICAL RULE: The system NEVER automatically engages a scammer. H.I.V.E.
activation requires explicit user consent at every step. No messages are ever
sent to a scammer by the system without the user consciously choosing to
ACTIVATE H.I.V.E. via the API or dashboard.

================================================================================
2. THE H.I.V.E. CONCEPT
================================================================================

H.I.V.E. stands for: Heuristic Intelligence & Virtual Entrapment

Conceptual pipeline:
  Detect  →  Engage  →  Extract  →  Report

ScamTracer AI adaptation of this pipeline:

  Incoming Conversation
    → Scam Detection (R ML + rule-based indicators)
    → User Notification (alert created)
    → User explicitly chooses one of:
          Option 1: BLOCK & PROTECT  — end interaction safely, no engagement
          Option 2: ACTIVATE H.I.V.E. — begin controlled, logged engagement

    → If H.I.V.E. is activated:
          Controlled Engagement (Node.js generates probing responses)
            → Intelligence Extraction (R extracts entities from conversation)
                (phone numbers, UPI IDs, URLs, emails, bank names,
                 transaction IDs, OTP requests, payment requests,
                 credential requests)
            → Behaviour Analysis (R detects scam patterns)
                (urgency, threats, impersonation, escalation, repeated requests)
            → Investigation Report (Shiny dashboard + factual statements)

The H.I.V.E. engine generates deterministic, rule-based probing responses.
It uses no external LLM or AI service. It never provides real credentials,
OTPs, or payment authorisations to the scammer.

3. HOW THE SYSTEM WORKS (END-TO-END FLOW)
================================================================================

--- DETECTION PHASE ---

Step 1: A WhatsApp message arrives.
        WhatsApp Web (whatsapp-web.js) intercepts the message in real time.
        Non-text messages (stickers, images, reactions) are skipped.

Step 2: Node.js sends the message text to the R Plumber API (POST /analyze).

Step 3: R analyses the message using two independent engines:
        (a) ML Classification — Logistic Regression (Elastic Net), trained on
            5,171 SMS messages, produces a spam probability (0–1).
        (b) Rule-based Indicator Engine — 14 regex-pattern indicators
            (OTP requests, account suspension threats, urgent language,
            prize claims, UPI/payment references, etc.) produce an
            indicator score (0–40).
        Combined risk_score = round(ml_probability × 60 + min(40, indicators))
        Risk levels: LOW (<30), MEDIUM (30–59), HIGH (≥60).

Step 4: If risk_score ≥ 60 (configurable threshold), Node.js creates an alert
        and the Chrome extension shows a floating panel on WhatsApp Web with:
          - Sender, risk score, risk level, ML prediction
          - Full message text (truncated at 200 chars)
          - Detected indicator list
          - Two action buttons: BLOCK & PROTECT | ACTIVATE H.I.V.E.

--- DECISION PHASE ---

Step 5: The user sees the alert and makes a conscious decision:
        - BLOCK & PROTECT → session state becomes BLOCKED. No further action.
        - ACTIVATE H.I.V.E. → session state becomes HIVE_ACTIVE.

--- H.I.V.E. ENGAGEMENT PHASE (only if user chose ACTIVATE H.I.V.E.) ---

Step 6: With session in HIVE_ACTIVE state, each scammer message is submitted
        via POST /hive/message. The H.I.V.E. engine analyses the message and
        selects a probing strategy (otp_deflection, payment_probe, url_probe,
        etc.) and returns a probing response. Conversation is recorded.

Step 7: After enough turns, the user ends the session via POST /hive/end.
        Session state becomes HIVE_ENDED.

--- INVESTIGATION PHASE ---

Step 8: POST /investigate triggers R to analyse the full conversation:
        (a) extract_entities() finds: PHONE, UPI_ID, URL, EMAIL, BANK_NAME,
            TRANSACTION_ID, OTP_REQUEST, PAYMENT_REQUEST, CREDENTIAL_REQUEST.
        (b) analyze_behaviour() detects: URGENCY, THREAT, IMPERSONATION,
            OTP_SOLICITATION, PAYMENT_REQUEST, CREDENTIAL_REQUEST,
            REPEATED_REQUEST, ESCALATION.
        (c) investigate_session() produces factual summary statements using
            cautious language ("Observed..."), never asserting identity.

--- VISUALISATION PHASE ---

Step 9: The R Shiny dashboard (port 4000) displays the complete investigation
        across 7 tabs:
          Tab 1 — Overview / Risk      (score, level, prediction, indicators)
          Tab 2 — H.I.V.E. Status      (state, turns, metadata)
          Tab 3 — Conversation         (styled full transcript)
          Tab 4 — Intelligence         (entity table + chart)
          Tab 5 — Behaviour Analysis   (pattern table + chart)
          Tab 6 — Investigation Summary (statements, escalation, disclaimers)
          Tab 7 — Live Monitor         (real-time WhatsApp alert feed)

7.1  R ANALYTICS ENGINE
────────────────────────────────────────────────────────────────────────────────

R is the sole analytical core. Node.js never performs any analytical work.

  R/utils/helpers.R — detect_indicators(text), indicator_summary(indicators)
    14 rule-based scam indicator patterns, each with a weight, severity, and
    regex. Examples:
      - OTP Request (weight 12, HIGH)
      - Account Suspension Threat (weight 10, HIGH)
      - Urgent Language (weight 6, MEDIUM)
      - Prize / Reward Claim (weight 8, MEDIUM)
      - UPI ID / Payment Reference (weight 8, HIGH)
      - Phone Number in Message (weight 6, MEDIUM)
      - Banking / Account Language (weight 5, MEDIUM)
      - Financial / Payment Language (weight 7, HIGH)
      - Credential Sharing Request (weight 10, HIGH)
      ... and more
    Indicator score is capped at 40 to prevent over-triggering on heuristics.

  R/analysis/risk_scorer.R — predict_scam(text), analyze_risk(message)
    predict_scam(): Phase 3 interface — loads model, tokenises text against
      the 508-term vocabulary, computes TF-IDF vector, runs glmnet prediction.
      Returns: predicted_class, spam_probability, risk_level, heuristic_flags.
    analyze_risk(): Phase 4 interface — calls predict_scam() then
      detect_indicators(), combines results into a 0–100 risk score.
      Returns: prediction, model_probability, ml_score, indicator_score,
               risk_score, risk_level, detected_indicators, explanations, caveat.

  R/analysis/intelligence_extractor.R — extract_entities(), investigate_session()
    extract_entities(conversation): scans each turn with 9 regex pattern sets.
    investigate_session(session_id, conversation): orchestrates full extraction
      + behaviour analysis, returns structured summary with factual statements.
      Safety: never fabricates evidence. Only extracts what is in the text.
      Language: "Observed..." statements, never "this person is a scammer."

  R/analysis/behaviour_analyzer.R — analyze_behaviour(conversation)
    Analyses INCOMING turns only. Detects URGENCY, THREAT, IMPERSONATION,
    OTP_SOLICITATION, PAYMENT_REQUEST, CREDENTIAL_REQUEST, REPEATED_REQUEST
    (same category in 2+ turns), ESCALATION (rising severity rank over turns).
    Escalation rank system: 1=impersonation, 2=urgency, 3=threat, 4=OTP,
                            5=credential, 6=payment.

7.2  R PLUMBER API (PORT 8000)
────────────────────────────────────────────────────────────────────────────────

File: R/api/plumber.R
Start: Rscript -e 'pr <- plumber::plumb("R/api/plumber.R"); pr$run(host="0.0.0.0", port=8000)'

  GET  /health      — Returns: status, service, version, r_version, model_loaded,
                       model_name (Logistic Regression Elastic Net), model_f1,
                       model_auc. Does NOT run a prediction.

  POST /analyze     — Input: {"message": "<text>"}
                       Calls analyze_risk() and returns the full result JSON.
                       Validates input; returns HTTP 400 for invalid input.
                       Returns HTTP 500 on analysis failure (no stack trace).

  POST /investigate — Input: {"session_id": "<id>", "conversation": [...]}
                       Calls investigate_session() and returns entities,
                       behaviours, and investigation summary statements.

  CORS filter: all origins permitted (development only).
  Serializer: auto_unbox=TRUE — clean JSON, no array-wrapped scalars.
  Environment: all R modules sourced with local=environment() so functions
               are visible to Plumber handler closures.

7.4  CHROME EXTENSION (WHATSAPP WEB UI)
────────────────────────────────────────────────────────────────────────────────

The extension runs on https://web.whatsapp.com/* and shows a floating alert
panel whenever a suspicious message is detected.

  manifest.json    — MV3; content script on WhatsApp Web; background service
                     worker; host_permissions for http://localhost:3000/*

  background.js    — Service worker handling messages from content.js:
                       FETCH_ALERTS   → GET /alerts
                       FETCH_STATUS   → GET /whatsapp/status
                       POST_DECISION  → POST /alerts/:id/decision
                     All HTTP goes through the service worker (content scripts
                     cannot make HTTP requests from an HTTPS page to localhost).

  content.js       — Polls GET /alerts every 2 seconds
                     shouldShowAlert(): shows panel if status=USER_DECISION_REQUIRED
                       AND risk_score >= 60
                     Deduplicates by alert_id (Set)
                     renderPanel(): shows sender, risk badge, message text
                       (200-char limit), detected indicators as bullet list
                     Buttons: BLOCK & PROTECT | ACTIVATE H.I.V.E.
                     Context-invalidation safety: _contextValid flag +
                       safeSendMessage() wrapper catches chrome.runtime.lastError
                     NEVER calls WhatsApp Web internal APIs
                     NEVER sends messages to contacts

  popup.html/js    — Toolbar popup showing: backend connection status,
                     WhatsApp state, risk threshold, pending alert count,
                     and preview of up to 3 pending alerts.

  styles.css       — Fixed top-right floating panel, colour-coded by risk:
                       HIGH/critical = red, MEDIUM = amber, LOW = green
                       Slide-in animation.

Safety constraints (all enforced and verified by tests):
  - Extension never sends a message to the suspicious sender
  - Extension never automatically activates H.I.V.E.
  - Extension never exposes risk analysis to the scammer
  - content.js contains zero WhatsApp Web internal API calls (verified by E4 test)
  - Alert panel cannot be dismissed without making an explicit decision

8. DATASET
================================================================================

Name     : UCI SMS Spam Collection v.1
Source   : UCI Machine Learning Repository
URL      : https://archive.ics.uci.edu/dataset/228/sms+spam+collection
License  : Creative Commons Attribution 4.0 International (CC BY 4.0)
Citation : Almeida, T. & Hidalgo, J. (2011). SMS Spam Collection [Dataset].
           UCI Machine Learning Repository. https://doi.org/10.24432/C5CC84

Raw records       : 5,574
After dedup       : 5,171 (403 exact duplicates removed)
ham (legitimate)  : 4,518 (87.37%)
spam              : 653   (12.63%)
Columns           : 11 (label, spam_label, text, char_count, word_count,
                    has_url, has_phone, has_currency, has_free, has_urgent,
                    has_prize)

Key EDA findings:
  - Spam messages average 138.7 characters vs 71.5 for ham (spam = longer)
  - Phone numbers present in 75.6% of spam vs 0.1% of ham
  - Currency symbols in 34.7% of spam vs 0.4% of ham
  - URLs in 14.1% of spam vs 0% of ham
  - "free" keyword in 22.8% of spam vs 1.2% of ham

Known limitation: Dataset is UK/Singapore-origin English SMS. India-specific
scam patterns (UPI IDs, OTP fraud, KYC fraud, NEFT/IMPS) are NOT in the
training data. The ML model may score India-specific scam messages as
LEGITIMATE. The rule-based indicator engine and Phase 9 entity extraction
compensate for this independently of the ML model.

Preprocessing (cleaner.R):
  - Removed 403 duplicate rows
  - Trimmed whitespace
  - Added binary spam_label, char_count, word_count, entity flags
  - URLs, phone numbers, currency symbols deliberately NOT stripped
    (needed for H.I.V.E. intelligence extraction in Phase 9)

NLP feature extraction (text_features.R):
  - Tokenised to unigrams (tidytext::unnest_tokens)
  - Removed standard stop words (with exceptions: free, win, urgent, otp,
    upi, kyc, blocked, credit, loan, award, claim, etc.)
  - Removed pure-number tokens and single-character tokens
  - TF-IDF computed via tidytext::bind_tf_idf
  - Top 500 terms selected by max TF-IDF
  - Pivoted to document × term matrix (5,171 × 510)

10. RISK SCORING SYSTEM
================================================================================

Function: analyze_risk(message) in R/analysis/risk_scorer.R

Formula:
  ml_score        = spam_probability × 60           range: [0.0, 60.0]
  indicator_score = min(40, sum(indicator_weights))  range: [0, 40], capped
  risk_score      = round(ml_score + indicator_score) range: [0, 100]

Risk levels:
  LOW     : risk_score < 30
  MEDIUM  : risk_score 30–59
  HIGH    : risk_score ≥ 60

Alert threshold (for WhatsApp live monitor): default 60 (configurable via
  SCAMTRACER_RISK_THRESHOLD environment variable).

Decision policy (Node.js state machine):
  LOW risk    → NORMAL state (no alert, no user action required)
  MEDIUM risk → USER_DECISION_REQUIRED (alert created, user must decide)
  HIGH risk   → USER_DECISION_REQUIRED (NOT automatic HIVE_ACTIVE)

The 60/40 split rationale:
  ML model is the primary evidence source (60%). Rule-based indicators are
  supplementary and capped (40%) to prevent false HIGH ratings from heuristics
  alone when the ML model is uncertain.

13. H.I.V.E. CONTROLLED ENGAGEMENT — RESPONSE STRATEGIES
================================================================================

File: nodejs/src/hiveEngine.js
Function: generateResponse(message, interactionCount)

The H.I.V.E. engine is fully deterministic and rule-based. No external LLM.
No AI API calls. No real credentials, OTPs, or payments ever generated.

7 response strategies, each with 3 cycling response templates:

  Strategy               Trigger Patterns
  ─────────────────────────────────────────────────────────────────────────────
  otp_deflection         "otp", "6-digit", "one-time code/password"
  credential_deflection  "password", "pin", "cvv", "net banking"
  payment_probe          "transfer", "upi id", "send money", "neft"
  suspension_probe       "suspend", "freeze", "deactivate", "block"
  url_probe              "http://", "www.", "click here", "open link"
  prize_probe            "won", "prize", "lottery", "congratulation"
  neutral_clarification  (fallback — no other pattern matched)

Template cycling: templates rotate by interaction_count mod 3, so turns 1/4/7
use template 1, turns 2/5/8 use template 2, turns 3/6/9 use template 3.
This prevents identical responses across multiple turns.

All H.I.V.E. responses are probing questions only — they ask for details,
question official documentation, or request verification. They never provide
credentials, authorise payments, or accept scammer claims.

15. STATE MACHINE — SESSION FLOW
================================================================================

Sessions are created by POST /message (when R returns MEDIUM or HIGH risk).
Sessions are in-memory only (cleared on server restart — demo-level).

  State                  Description
  ─────────────────────────────────────────────────────────────────────────────
  NORMAL                 LOW risk — no user action required
  USER_DECISION_REQUIRED MEDIUM or HIGH risk — user must choose an action
  BLOCKED                User chose BLOCK & PROTECT — conversation ended safely
  HIVE_ACTIVE            User explicitly activated H.I.V.E. — engagement active
  HIVE_ENDED             User ended H.I.V.E. session — ready for investigation

Transitions:
  POST /message (LOW)       → NORMAL
  POST /message (MED/HIGH)  → USER_DECISION_REQUIRED
  POST /decision BLOCK      → BLOCKED
  POST /decision ACTIVATE   → HIVE_ACTIVE
  POST /hive/end            → HIVE_ENDED

Enforced state conflicts (HTTP 409):
  BLOCKED + ACTIVATE_HIVE     → 409 ALREADY_BLOCKED
  HIVE_ACTIVE + ACTIVATE_HIVE → 409 ALREADY_ACTIVE
  NORMAL + any decision        → 409 NO_DECISION_REQUIRED
  HIVE_ENDED + /hive/end       → 409 ALREADY_ENDED
  Unknown session              → 404 SESSION_NOT_FOUND

Alert states (separate from sessions — for WhatsApp live monitor):
  USER_DECISION_REQUIRED, BLOCKED, HIVE_ACTIVE, HIVE_ENDED

19. KNOWN LIMITATIONS
================================================================================

1. INDIA-SPECIFIC ML SCORES
   The ML model is trained on UK/Singapore SMS (UCI dataset). India-specific
   scam patterns (UPI IDs, KYC fraud, OTP fraud, SBI/HDFC terminology) may
   score as LEGITIMATE by the ML model. The rule-based indicator engine and
   Phase 9 entity extraction compensate independently. A high indicator_score
   will push the composite risk_score to MEDIUM or HIGH regardless of ML.

2. IN-MEMORY SESSION AND ALERT STORES
   Sessions and alerts are in-memory only. They are cleared on server restart.
   This is acceptable for a college project demo. Production use would require
   persistent storage.

3. NAIVE BAYES INCOMPATIBILITY
   Naive Bayes gave degenerate all-spam predictions (AUC=0.50). Expected:
   Gaussian NB is incompatible with sparse TF-IDF features. If NB is needed,
   Multinomial NB with raw term counts must be used. Documented as a teaching point.

4. PREDICTION RE-TOKENISES ON EVERY CALL
   predict_scam() loads and processes the model on each call. Acceptable for
   demo; would need caching for a high-throughput production service.

5. ENTITY EXTRACTION IS REGEX-ONLY
   No semantic NLP. Unusual phrasings may not be detected. BANK_NAME uses a
   curated 20-entry dictionary, not an exhaustive list.

6. EXTENSION INITIAL-ALERT UI REGRESSION
   The Chrome extension's initial-alert display has a known regression under
   investigation (Review 3 checkpoint). The backend and analysis pipeline
   are unaffected.

7. RENV OUT-OF-SYNC WARNING
   A cosmetic warning may appear when running R scripts. Run renv::snapshot()
   to resolve if needed.

8. LOCAL DEVELOPMENT ONLY
   No authentication, no HTTPS, no rate limiting, no production hardening.
   Suitable for college project demonstration only.

20. IMPORTANT DESIGN DECISIONS
================================================================================

 1. R is the ONLY analytical technology. Node.js never calculates risk scores,
    performs ML inference, or analyses text.

 2. Node.js is the ONLY communication technology. R never handles HTTP directly
    (except via Plumber which is R's web framework).

 3. User consent model: H.I.V.E. is NEVER activated automatically. Even a
    risk_score of 100 only creates a USER_DECISION_REQUIRED state. The user
    must explicitly call POST /decision with action=ACTIVATE_HIVE.

 4. No fabricated data: All model metrics, EDA statistics, entity extractions,
    and behaviour detections come from real function calls. Nothing is invented.

 5. 60/40 ML-to-indicator split: ML is primary evidence (60%); indicators are
    supplementary and capped at 40%. This prevents false HIGH ratings from
    heuristics alone.

 6. lambda.1se for glmnet: Prefers simpler model. Reduces overfitting on the
    508-dimensional sparse feature space.

 7. vapply over sapply in indicator_summary(): Handles empty indicator lists
    safely without type coercion surprises.

 8. UPI vs email disambiguation: Same base regex matches both. Emails are
    classified by requiring a TLD (\.[A-Za-z]{2,}$). UPI IDs (no TLD) are
    classified separately. No double-counting.

 9. Digit-required TRANSACTION_ID: Pattern requires at least one digit to
    prevent matching plain English words when ignore_case=TRUE.

10. NULL text guard in R list processing: as.character(NULL) returns
    character(0), not NA. Guard: if (!is.null(t$text)) as.character(t$text)
    else NA_character_.

11. simplifyVector=FALSE in POST /investigate: Preserves conversation as
    list-of-lists rather than coercing to a data frame.

12. source(..., local=environment()) in Plumber: Makes R functions visible to
    handler closures in the Plumber router's private environment.

13. Chrome extension HTTP via service worker: Content scripts cannot make HTTP
    requests from an HTTPS page to localhost. All HTTP goes through background.js.

14. Defence-in-depth for alert creation: 5 validation layers:
    plumber.R (NA_real_ not NULL) → normalizeWhatsAppMessage → validateRiskResult
    → processIncomingWhatsAppMessage guard → createAlert guard.
